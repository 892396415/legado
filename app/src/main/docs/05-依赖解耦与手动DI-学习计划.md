# 依赖解耦与手动 DI - 详细学习计划

> 基于 Legado 项目学习 Android 手动依赖注入与单例模式

---

## 一、概述

### 1.1 什么是依赖注入

依赖注入（Dependency Injection，简称 DI）是一种设计模式，其核心思想是：

> **将对象的创建和依赖关系的管理，从对象内部移到外部容器或调用方。**

简单来说，不是在类内部 `new` 一个依赖对象，而是由外部传入。

**传统方式（耦合度高）：**
```kotlin
class BookViewModel {
    // 直接在内部创建依赖
    private val bookDao = BookDao()  
    private val httpClient = OkHttpClient()
}
```

**依赖注入方式（解耦）：**
```kotlin
class BookViewModel(
    private val bookDao: BookDao,      // 从外部注入
    private val httpClient: OkHttpClient
)
```

### 1.2 常见的 DI 方案对比

| 方案 | 特点 | 适用场景 |
|------|------|----------|
| **手动 DI** | 纯代码实现，无框架依赖 | 中小型项目，学习成本低 |
| **Hilt** | Google 官方推荐，基于 Dagger | 大型项目，Android 官方支持 |
| **Dagger 2** | 编译时生成代码，性能好 | 大型项目，学习成本高 |
| **Koin** | Kotlin 原生，运行时注入 | Kotlin 项目，轻量级 |

### 1.3 Legado 的选择

Legado 项目选择 **手动 DI**，原因如下：

1. **项目规模适中**：不需要复杂的依赖图
2. **编译速度**：避免注解处理器带来的编译时间增加
3. **代码可控性**：依赖关系清晰可见
4. **学习成本**：团队无需学习 Dagger/Hilt

## 二、核心实现方式

### 2.1 Kotlin `object` 单例模式

Kotlin 的 `object` 关键字天然支持单例模式，这是 Legado 项目中最常用的依赖管理方式。

**文件位置**：`app/src/main/java/io/legado/app/help/config/AppConfig.kt`

```kotlin
@Suppress("MemberVisibilityCanBePrivate", "ConstPropertyName")
object AppConfig : SharedPreferences.OnSharedPreferenceChangeListener {
    
    // 全局配置属性
    var userAgent: String = getPrefUserAgent()
    var isEInkMode = appCtx.getPrefString(PreferKey.themeMode) == "3"
    var themeMode = appCtx.getPrefString(PreferKey.themeMode, "0")
    
    // 监听配置变化
    override fun onSharedPreferenceChanged(
        sharedPreferences: SharedPreferences?, 
        key: String?
    ) {
        when (key) {
            PreferKey.themeMode -> {
                themeMode = appCtx.getPrefString(PreferKey.themeMode, "0")
                isEInkMode = themeMode == "3"
            }
            // ... 其他配置更新
        }
    }
    
    // 业务方法
    var isNightTheme: Boolean
        get() = when (themeMode) {
            "1" -> false
            "2" -> true
            else -> sysConfiguration.isNightMode
        }
        set(value) {
            if (isNightTheme != value) {
                if (value) {
                    appCtx.putPrefString(PreferKey.themeMode, "2")
                } else {
                    appCtx.putPrefString(PreferKey.themeMode, "1")
                }
            }
        }
}
```

**使用方式：**
```kotlin
// 在任何地方直接使用
val isNight = AppConfig.isNightTheme
AppConfig.themeMode = "2"
```

**优点：**
- 线程安全（Kotlin 保证）
- 懒加载（首次访问时初始化）
- 代码简洁

### 2.3 复杂依赖的封装

**文件位置**：`app/src/main/java/io/legado/app/help/CacheManager.kt`

```kotlin
@Keep
@Suppress("unused")
object CacheManager {

    // 三层缓存架构
    private val queryTTFMap = hashMapOf<String, Pair<Long, QueryTTF>>()

    // 内存缓存 - 50MB LruCache
    private val memoryLruCache = object : LruCache<String, Any>(1024 * 1024 * 50) {
        override fun sizeOf(key: String, value: Any): Int {
            return value.toString().memorySize()
        }
    }

    // 存储数据（自动选择存储层）
    @JvmOverloads
    fun put(key: String, value: Any, saveTime: Int = 0) {
        val deadline = if (saveTime == 0) 0 
                       else System.currentTimeMillis() + saveTime * 1000
        
        when (value) {
            is QueryTTF -> queryTTFMap[key] = Pair(deadline, value)
            is ByteArray -> ACache.get().put(key, value, saveTime)
            else -> {
                val cache = Cache(key, value.toString(), deadline)
                putMemory(key, value)
                appDb.cacheDao.insert(cache)  // 使用全局 appDb
            }
        }
    }

    // 读取数据（先内存后数据库）
    fun get(key: String): String? {
        // 1. 先查内存
        getFromMemory(key)?.let {
            if (it is String) return it
        }
        
        // 2. 再查数据库
        val cache = appDb.cacheDao.get(key)
        if (cache != null && (cache.deadline == 0L || 
            cache.deadline > System.currentTimeMillis())) {
            putMemory(key, cache.value ?: "")
            return cache.value
        }
        return null
    }
}
```

**依赖关系：**
```
CacheManager (单例)
├── memoryLruCache (内部 LruCache)
├── queryTTFMap (内部 HashMap)
├── ACache.get() (文件缓存)
└── appDb (全局数据库单例)
```

```kotlin
// 扩展函数 - 不需要单例，直接使用
suspend fun OkHttpClient.newCallResponse(
    retry: Int = 0,
    builder: Request.Builder.() -> Unit
): Response {
    val requestBuilder = Request.Builder()
    requestBuilder.apply(builder)
    var response: Response? = null
    for (i in 0..retry) {
        response = newCall(requestBuilder.build()).await()
        if (response.isSuccessful) {
            return response
        }
    }
    return response!!
}

// Call 扩展 - 协程支持
suspend fun Call.await(): Response = suspendCancellableCoroutine { block ->
    block.invokeOnCancellation {
        cancel()
    }
    enqueue(object : Callback {
        override fun onFailure(call: Call, e: IOException) {
            block.resumeWithException(e)
        }
        override fun onResponse(call: Call, response: Response) {
            block.resume(response)
        }
    })
}
```

**使用示例：**

```kotlin
            // 解析响应
```

### 4.2 Cookie 管理单例

**文件位置**：`app/src/main/java/io/legado/app/help/http/CookieManager.kt`

```kotlin
object CookieManager {
    
    // 依赖 appDb 数据库
    private val cookieDao: CookieDao
        get() = appDb.cookieDao

    fun saveCookie(url: String, cookie: String) {
        val httpUrl = url.toHttpUrl()
        val cookieList = Cookie.parseAll(httpUrl, Headers.Builder()
            .add("Set-Cookie", cookie)
            .build())
        cookieList.forEach { parsedCookie ->
            val cookieEntity = Cookie(
                tag = "",
                url = url,
                name = parsedCookie.name,
                value = parsedCookie.value,
                domain = parsedCookie.domain
            )
            cookieDao.insert(cookieEntity)
        }
    }

    fun getCookies(url: String): List<Cookie> {
        return cookieDao.getByUrl(url).map { entity ->
            Cookie.Builder()
                .name(entity.name)
                .value(entity.value)
                .domain(entity.domain)
                .build()
        }
    }
}
```

## 六、手动 DI 的优缺点

### 6.1 优点

| 优点 | 说明 |
|------|------|
| **简单直观** | 依赖关系一目了然，无需学习框架 |
| **编译速度快** | 没有注解处理器，编译时间更短 |
| **调试容易** | 所有代码都是自己写的，容易定位问题 |
| **无反射开销** | 运行时没有反射带来的性能损耗 |
| **代码可控** | 可以精确控制初始化时机 |

### 6.2 缺点

| 缺点 | 说明 |
|------|------|
| **样板代码** | 需要手动编写依赖获取代码 |
| **不易测试** | 直接使用单例，难以 Mock 替换 |
| **生命周期管理** | 需要手动管理对象的生命周期 |
| **依赖不透明** | 类的依赖关系不体现在构造函数中 |
| **大型项目困难** | 依赖复杂时管理困难 |

### 6.3 测试问题及解决方案

**问题：单例难以 Mock**
```kotlin
class BookViewModel {
    // 难以在测试中替换 appDb
    private val bookDao = appDb.bookDao
}
```

**解决方案 1：使用接口抽象**
```kotlin
interface BookRepository {
    suspend fun getBook(url: String): Book?
}

object BookRepositoryImpl : BookRepository {
    private val bookDao = appDb.bookDao
    override suspend fun getBook(url: String) = bookDao.getBook(url)
}

class BookViewModel(
    private val repository: BookRepository = BookRepositoryImpl
) {
    // 测试时可以传入 MockRepository
}
```

**解决方案 2：使用 var 变量（测试时替换）**
```kotlin
object BookRepository {
    var bookDao: BookDao = appDb.bookDao
        private set

    // 仅测试使用
    fun setBookDaoForTest(dao: BookDao) {
        bookDao = dao
    }
}
```

#### 目标
理解什么是依赖注入，为什么需要依赖注入
依赖注入就是把原本由类内部创建实例改变为由外部传入对象的实现方式
打个比方：
 传统方式：你自己做饭（自己创建依赖），想换菜系就要学新做法
 依赖注入：外卖送上门（外部注入），想换菜系换个外卖就行
#### 任务

   - [Android 官方依赖注入指南](https://developer.android.com/training/dependency-injection)

理解控制反转（IoC）概念
IoC = 你不再控制"对象怎么创建"，只控制"对象怎么用"
把创建对象的控制权从自己手里交给外部容器/框架，这就是"反转"的意义

2. **对比两种方式**
   ```kotlin

           .build().bookDao()

   // 方式2：依赖注入（松耦合）
   class BookViewModel(private val bookDao: BookDao)
   ```

#### 验证
能回答：什么是依赖注入？它解决了什么问题？
解决的问题:
1、解耦，降低类之间的依赖
2、方便测试，很容易就可以替换测试对象
3、依赖关系清晰，所需的依赖体现在创建对象的入参，而不是在内部偷偷的创建实例
4、组件可以复用，一个类只需要替换一下创建的参数就可以达到复用的效果

### 阶段二：分析项目中的单例模式（1-2天）

#### 目标
理解 Kotlin `object` 单例模式的实现原理
1. 编译为静态单例
   Kotlin object 编译后生成一个类，包含一个静态单例实例：
// Kotlin
object Singleton {
   fun doSomething() {}
}
// 编译生成后的Java类
public final class Singleton {
   public static final Singleton INSTANCE = new Singleton();

   private Singleton() {}  // 私有构造函数

   public final void doSomething() {}
}

#### 任务

1. **阅读 AppConfig.kt**
   - 分析 `object` 关键字的使用
   - 理解 SharedPreferences 监听机制

   **SharedPreferences 监听机制详解：**

   SharedPreferences 监听机制基于 **观察者模式**，当存储的配置值发生变化时，注册的监听器会收到回调通知。

   **核心接口：**
   ```kotlin
   interface OnSharedPreferenceChangeListener {
       fun onSharedPreferenceChanged(sharedPreferences: SharedPreferences?, key: String?)
   }
   ```

   **Legado 中的两种实现方式：**

   **方式一：全局单例监听（AppConfig）**

   AppConfig 是一个 Kotlin `object` 单例，实现了 `OnSharedPreferenceChangeListener` 接口：
   ```kotlin
   object AppConfig : SharedPreferences.OnSharedPreferenceChangeListener {
       var themeMode = appCtx.getPrefString(PreferKey.themeMode, "0")
       
       override fun onSharedPreferenceChanged(prefs: SharedPreferences?, key: String?) {
           when (key) {
               PreferKey.themeMode -> {
                   themeMode = appCtx.getPrefString(PreferKey.themeMode, "0")
               }
               // ... 其他配置更新
           }
       }
   }
   ```

   在 Application 中注册监听：
   ```kotlin
   class App : Application() {
       override fun onCreate() {
           super.onCreate()
           defaultSharedPreferences.registerOnSharedPreferenceChangeListener(AppConfig)
       }
   }
   ```

   **方式二：生命周期感知的监听（扩展函数）**

   通过 Lifecycle 自动管理监听器的注册和注销：
   ```kotlin
   fun LifecycleOwner.observeSharedPreferences(
       prefs: SharedPreferences = appCtx.defaultSharedPreferences,
       l: SharedPreferences.OnSharedPreferenceChangeListener
   ) {
       val observer = object : DefaultLifecycleObserver {
           override fun onCreate(owner: LifecycleOwner) {
               prefs.registerOnSharedPreferenceChangeListener(l)
           }

           override fun onDestroy(owner: LifecycleOwner) {
               prefs.unregisterOnSharedPreferenceChangeListener(l)
               lifecycle.removeObserver(this)
           }

           override fun onPause(owner: LifecycleOwner) {
               prefs.unregisterOnSharedPreferenceChangeListener(l)
           }

           override fun onResume(owner: LifecycleOwner) {
               prefs.registerOnSharedPreferenceChangeListener(l)
           }
       }
       lifecycle.addObserver(observer)
   }
   ```

   **两种方式的对比：**

   | 特性 | 全局单例监听 | 生命周期感知监听 |
   |------|------------|----------------|
   | 生命周期 | 与应用同生命周期 | 跟随 Activity/Fragment |
   | 内存泄漏风险 | 低（单例不持有 Activity 引用） | 已处理（自动注销） |
   | 适用场景 | 全局配置管理 | 页面级配置监听 |
   | 性能优化 | 持续监听 | Pause 时暂停，Resume 时恢复 |

   **关键实现要点：**

   1. **内存泄漏防护**：全局单例不持有 Activity 引用；Lifecycle 监听自动注销
   2. **性能优化**：后台页面暂停监听，返回前台恢复监听
   3. **数据同步**：监听器负责保持内存缓存与 SharedPreferences 同步
   4. **线程安全**：回调在主线程执行，避免耗时操作

 2. **阅读 AppDatabase.kt**
    - 分析 `by lazy` 延迟初始化
    - 理解数据库单例的创建

    **by lazy 延迟初始化详解：**

    `by lazy` 是 Kotlin 提供的属性委托机制，用于实现延迟初始化（首次访问时才初始化）。

    **基本语法：**
    ```kotlin
    val appDb by lazy {
        Room.databaseBuilder(appCtx, AppDatabase::class.java, "legado.db")
            .build()
    }
    ```

    **by lazy 的工作原理：**
    ```kotlin
    // 等价于以下 Java 代码
    private volatile AppDatabase _appDb = null;
    private final Object _appDb_lock = new Object();

    public AppDatabase getAppDb() {
        if (_appDb == null) {
            synchronized(_appDb_lock) {
                if (_appDb == null) {
                    _appDb = Room.databaseBuilder(...).build();
                }
            }
        }
        return _appDb;
    }
    ```

    **线程安全保证：**
    - `by lazy` 默认使用 `LazyThreadSafetyMode.SYNCHRONIZED` 模式
    - 使用双重检查锁定（Double-Checked Locking）确保线程安全
    - 初始化代码只执行一次

    **Room 数据库单例实现：**

    ```kotlin
    // 1. 顶层变量声明 - 全局可访问
    val appDb by lazy {
        Room.databaseBuilder(appCtx, AppDatabase::class.java, AppDatabase.DATABASE_NAME)
            // 2. 迁移策略配置
            .fallbackToDestructiveMigrationFrom(false, 1, 2, 3, 4, 5, 6, 7, 8, 9)
            .addMigrations(*DatabaseMigrations.migrations)
            // 3. 查询配置
            .allowMainThreadQueries()
            // 4. 生命周期回调
            .addCallback(AppDatabase.dbCallback)
            .build()
    }

    // 5. Room 数据库抽象类
    @Database(
        version = 76,                          // 数据库版本
        exportSchema = true,                   // 导出 schema
        entities = [Book::class, ...],         // 实体类列表
        views = [BookSourcePart::class],       // 视图
        autoMigrations = [                     // 自动迁移配置
            AutoMigration(from = 43, to = 44),
            AutoMigration(from = 54, to = 55, spec = DatabaseMigrations.Migration_54_55::class),
        ]
    )
    abstract class AppDatabase : RoomDatabase() {
        abstract val bookDao: BookDao
        abstract val bookGroupDao: BookGroupDao
        // ... 其他 DAO
    }
    ```

    **关键配置说明：**

    | 配置项 | 作用 | 说明 |
    |--------|------|------|
    | `fallbackToDestructiveMigrationFrom` | 破坏性迁移 | 指定版本从空数据库重建 |
    | `addMigrations` | 手动迁移 | 执行自定义迁移逻辑 |
    | `allowMainThreadQueries` | 主线程查询 | 允许在主线程执行查询（小心使用） |
    | `addCallback` | 生命周期回调 | 监听数据库创建/打开事件 |
    | `autoMigrations` | 自动迁移 | Room 自动生成迁移代码 |

    **数据库回调（dbCallback）：**

    ```kotlin
    val dbCallback = object : Callback() {
        override fun onCreate(db: SupportSQLiteDatabase) {
            // 数据库首次创建时执行
            db.setLocale(Locale.CHINESE)
        }

        override fun onOpen(db: SupportSQLiteDatabase) {
            // 数据库打开时执行
            // 插入默认数据、修复数据等
        }
    }
    ```

    **使用方式：**
    ```kotlin
    // 在任何地方直接访问
    val books = appDb.bookDao.getAll()
    appDb.bookSourceDao.insert(source)
    ```

    **object vs by lazy 对比：**

    | 特性 | object | by lazy |
    |------|--------|---------|
    | 初始化时机 | 类加载时 | 首次访问时 |
    | 初始化控制 | 无法控制 | 可控，可自定义复杂逻辑 |
    | 线程安全 | JVM 保证 | 默认 SYNCHRONIZED 模式 |
    | 适用场景 | 简单单例 | 需要复杂初始化的单例 |

    **为什么选择 by lazy 实现数据库单例：**

    1. **延迟初始化**：避免应用启动时立即初始化数据库
    2. **复杂配置**：需要配置迁移策略、回调等
    3. **线程安全**：默认线程安全，无需额外处理
    4. **懒加载**：如果某些功能未使用，数据库不会被创建

## 八、常见问题

### Q1: 为什么不用 Hilt/Dagger？

**答案：**

1. **项目规模**：Legado 是中型项目，手动 DI 已足够
2. **编译速度**：Hilt/Dagger 使用注解处理器，会增加编译时间
3. **学习成本**：团队成员无需学习复杂的框架
4. **代码可读性**：手动 DI 的依赖关系更直观

### Q2: 单例会不会导致内存泄漏？

**答案：**

正确使用不会：
1. 单例持有的是全局 Context（Application），不是 Activity
2. 使用弱引用持有可能有生命周期的对象
3. 及时清理不需要的引用

```kotlin
object MyManager {
    private var activityRef: WeakReference<Activity>? = null
    
    fun setActivity(activity: Activity) {
        activityRef = WeakReference(activity)
    }
}
```

### Q3: 如何处理多进程？

**答案：**

单例在多进程中每个进程都是独立的实例：

```kotlin
object MySingleton {
    init {
        // 每个进程都会执行一次
        Log.d("MySingleton", "Process: ${Process.myProcessName()}")
    }
}
```

如果需要跨进程共享数据，需要使用：
- ContentProvider
- AIDL
- SharedPreferences（MODE_MULTI_PROCESS）
- Room 数据库

### Q4: `object` 和 `companion object` 的区别？

**答案：**

```kotlin
// object - 全局单例
object MySingleton {
    fun doSomething() {}
}
// 调用：MySingleton.doSomething()

// companion object - 类级别单例
class MyClass {
    companion object {
        fun doSomething() {}
    }
}
// 调用：MyClass.doSomething()

// 区别：
// - object 是独立的单例类
// - companion object 是类的静态成员
```

## 十一、自测题目答案

### 题目 1：什么是依赖注入？

**答案：**

依赖注入（Dependency Injection，DI）是一种设计模式，其核心思想是**将对象的依赖从外部注入，而不是在对象内部创建**。

**传统方式（依赖在内部创建）：**
```kotlin
class BookViewModel {
    private val bookDao = BookDao()  // 内部创建依赖
}
```

**依赖注入方式（依赖从外部传入）：**
```kotlin
class BookViewModel(private val bookDao: BookDao)  // 外部传入依赖
```

**依赖注入的好处：**
1. **解耦**：类不依赖具体的实现
2. **可测试**：可以轻松替换依赖进行测试
3. **可维护**：依赖关系清晰可见
4. **可复用**：组件可以在不同上下文中复用

### 题目 2：`object` 单例模式是如何保证线程安全的？

**答案：**

Kotlin 的 `object` 单例模式在编译后转化为以下 Java 代码：

```kotlin
// Kotlin 代码
object MySingleton {
    fun doSomething() {}
}
```

```java
// 编译后的 Java 代码
public final class MySingleton {
    public static final MySingleton INSTANCE;
    
    static {
        INSTANCE = new MySingleton();
    }
    
    private MySingleton() {}
    
    public final void doSomething() {}
}
```

**线程安全保证：**

1. **静态初始化**：JVM 保证静态初始化块在类加载时执行，且只执行一次
2. **类加载机制**：JVM 的类加载器在多线程环境下会自动同步
3. **私有构造函数**：防止外部创建新实例

**关键点：** JVM 的类加载机制本身是线程安全的，所以 `object` 天然线程安全。

### 题目 3：`by lazy` 和 `object` 的区别是什么？

**答案：**

| 特性 | `object` | `by lazy` |
|------|----------|-----------|
| **初始化时机** | 类加载时 | 首次访问时 |
| **初始化控制** | 无法控制 | 可以控制 |
| **初始化逻辑** | 仅无参构造 | 可自定义复杂逻辑 |
| **线程安全** | JVM 保证 | 默认线程安全（可配置） |
| **使用场景** | 简单单例 | 复杂初始化单例 |

**代码对比：**

```kotlin
// object - 简单单例
object SimpleSingleton {
    val name = "Simple"
}

// by lazy - 复杂初始化
val complexSingleton by lazy {
    // 可以执行复杂的初始化逻辑
    val config = loadConfig()
    val db = createDatabase(config)
    ComplexSingleton(db)
}
```

**Legado 项目中的 `appDb` 使用 `by lazy` 的原因：**
```kotlin

        .allowMainThreadQueries()
        .addCallback(AppDatabase.dbCallback)

}
```

### 题目 5：手动 DI 相比 Hilt 有什么优缺点？

**答案：**

**手动 DI 的优点：**

| 优点 | 说明 |
|------|------|
| **简单直观** | 依赖关系直接在代码中体现，无需学习框架 |
| **编译速度快** | 没有注解处理器，编译时间更短 |
| **调试容易** | 所有代码都是自己写的，调用栈清晰 |
| **无运行时开销** | 没有反射，性能更好 |
| **代码量少** | 小型项目代码量更少 |

**手动 DI 的缺点：**

| 缺点 | 说明 |
|------|------|
| **样板代码** | 大量重复的依赖获取代码 |
| **测试困难** | 单例难以 Mock 替换 |
| **生命周期管理** | 需要手动管理对象的生命周期 |
| **依赖不透明** | 类的依赖关系不在构造函数中 |
| **扩展困难** | 项目变大后管理复杂 |

**Hilt 的优点：**
- 自动生成依赖注入代码
- 生命周期自动管理
- 支持作用域（@Singleton, @ActivityScoped）
- 测试友好（易于 Mock）
- 官方支持和维护

**Hilt 的缺点：**
- 学习成本高
- 编译时间增加
- 调试困难（生成的代码）
- 小项目过度设计

**选择建议：**
- 小型项目 → 手动 DI
- 中型项目 → 手动 DI 或 Koin
- 大型项目 → Hilt

### 题目 6：如何在测试中替换单例依赖？

**答案：**

**方法 1：使用接口抽象**

```kotlin
// 定义接口
interface BookRepository {
    suspend fun getBook(url: String): Book?
}

// 真实实现
object BookRepositoryImpl : BookRepository {
    private val bookDao = appDb.bookDao
    override suspend fun getBook(url: String) = bookDao.getBook(url)
}

// ViewModel 通过接口依赖
class BookViewModel(
    private val repository: BookRepository = BookRepositoryImpl
) {
    fun loadBook(url: String) {
        execute { repository.getBook(url) }
    }
}

// 测试代码
@Test
fun testBookViewModel() {
    val mockRepository = object : BookRepository {
        override suspend fun getBook(url: String) = Book(name = "Test Book")
    }
    val viewModel = BookViewModel(mockRepository)
}
```

**方法 2：使用 var 变量替换**

```kotlin
object BookRepository {
    var bookDao: BookDao = appDb.bookDao
        private set

    // 仅测试使用
    @VisibleForTesting
    fun setBookDaoForTest(dao: BookDao) {
        bookDao = dao
    }
}

// 测试代码
@Test
fun testBookRepository() {
    val mockDao = mockk<BookDao>()
    BookRepository.setBookDaoForTest(mockDao)
    // 测试逻辑
}
```

**方法 3：使用依赖注入容器**

```kotlin
// 简单的 DI 容器
object DI {
    var bookDao: BookDao by lazy { appDb.bookDao }
    var bookSourceDao: BookSourceDao by lazy { appDb.bookSourceDao }
    
    @VisibleForTesting
    fun reset() {
        // 重置所有依赖
    }
}

// 测试代码
@Test
fun test() {
    DI.bookDao = mockk()
    // 测试逻辑
}
```
