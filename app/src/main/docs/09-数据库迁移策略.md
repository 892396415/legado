## 一、迁移基础概念

### 1.1 什么是数据库迁移

**数据库迁移**是指在应用升级时，将旧版本数据库结构转换为新版本的过程。

```
应用版本 1.0          应用版本 2.0
    │                      │
    ▼                      ▼
┌──────────┐           ┌──────────┐
│ DB v10   │  ──────▶  │ DB v11   │
│          │   迁移    │          │
│ 表: books│           │ 表: books│
│ 字段:    │           │ 字段:    │
│  - name  │           │  - name  │
│  - author│           │  - author│
│          │           │  + price │ ← 新增字段
└──────────┘           └──────────┘
```

### 1.2 为什么要迁移

**不迁移的后果：**
```
用户安装新版本
    │
    ▼
┌─────────────────────┐
│ Room 检测到版本变化 │
│ v10 → v11           │
└─────────────────────┘
    │
    ▼
┌─────────────────────┐
│ 没有找到迁移方案    │
└─────────────────────┘
    │
    ▼
┌─────────────────────┐
│ 抛出异常            │
│ IllegalStateException│
│ "Room cannot verify │
│  the data integrity"│
└─────────────────────┘
    │
    ▼
应用崩溃
```

### 1.3 Legado 项目迁移演进

```
版本 1-9 (早期):   破坏性迁移    → 数据丢失可接受
版本 10-43:        手动迁移      → 32 个 Migration 类
版本 44-76:        自动迁移      → 34 个 AutoMigration
```

## 二、三种迁移策略对比

| 策略 | 数据保留 | 实现复杂度 | 适用场景 | Legado 使用 |
|------|---------|-----------|---------|------------|
| **破坏性迁移** | ❌ 全部丢失 | ⭐ 最简单 | 开发测试、缓存数据 | 版本 1-9 |
| **手动迁移** | ✅ 完整保留 | ⭐⭐⭐ 复杂 | 复杂变更、数据转换 | 版本 10-43 |
| **自动迁移** | ✅ 基本保留 | ⭐ 简单 | 简单变更（增删表/列） | 版本 44-76 |

### 2.1 策略选择决策树

```
数据库结构变更？
    │
    ├── 删除表/清空数据？
    │       └── 破坏性迁移
    │
    ├── 简单变更？（仅增删表/列）
    │       └── 自动迁移
    │
    ├── 复杂变更？（重构表结构）
    │       └── 手动迁移
    │
    └── 需要数据转换？
            ├── 自动迁移 + Spec
            └── 手动迁移
```

## 三、破坏性迁移

### 3.1 原理

**破坏性迁移**直接删除旧数据库文件，创建全新的空数据库。

```kotlin
// 配置方式 1：所有版本都破坏性迁移
.fallbackToDestructiveMigration()

// 配置方式 2：指定版本破坏性迁移（Legado 使用）
.fallbackToDestructiveMigrationFrom(false, 1, 2, 3, 4, 5, 6, 7, 8, 9)
```

### 3.2 Legado 实践

**AppDatabase.kt 配置：**
```kotlin
val appDb by lazy {
    Room.databaseBuilder(appCtx, AppDatabase::class.java, "legado.db")
        // 版本 1-9 升级时删除重建
        .fallbackToDestructiveMigrationFrom(false, 1, 2, 3, 4, 5, 6, 7, 8, 9)
        // 版本 10-43 使用手动迁移
        .addMigrations(*DatabaseMigrations.migrations)
        .build()
}
```

**为什么版本 1-9 使用破坏性迁移？**
- 早期版本数据结构不稳定
- 用户量小，数据丢失影响小
- 简化开发和测试

### 3.3 适用场景

✅ **适合使用：**
- 开发/测试阶段
- 缓存数据库（可重新生成）
- 首次发布前的快速迭代
- 用户明确同意的数据重置

❌ **避免使用：**
- 用户的阅读记录
- 书源配置
- 书籍收藏
- 任何不可恢复的数据

## 四、手动迁移详解

### 4.1 基础结构

```kotlin
// 定义 Migration
val migration_10_11 = object : Migration(10, 11) {
    override fun migrate(database: SupportSQLiteDatabase) {
        // 执行 SQL 语句
        database.execSQL("SQL语句")
    }
}

// 添加到数据库配置
.addMigrations(migration_10_11)
```

### 4.2 常用 SQL 操作

#### 4.2.1 添加列（ALTER TABLE ADD）

```kotlin
// migration_11_12: 添加 style 列
private val migration_11_12 = object : Migration(11, 12) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL("ALTER TABLE rssSources ADD style TEXT")
    }
}

// migration_12_13: 添加非空列（必须指定 DEFAULT）
private val migration_12_13 = object : Migration(12, 13) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL(
            "ALTER TABLE rssSources ADD articleStyle INTEGER NOT NULL DEFAULT 0"
        )
    }
}
```

**⚠️ 重要：** 添加非空列必须提供 `DEFAULT` 值，否则 SQL 会失败。

#### 4.2.2 创建新表（CREATE TABLE）

```kotlin
// migration_15_17: 创建阅读记录表
private val migration_15_17 = object : Migration(15, 17) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL(
            """CREATE TABLE IF NOT EXISTS `readRecord` 
                (`bookName` TEXT NOT NULL, 
                 `readTime` INTEGER NOT NULL, 
                 PRIMARY KEY(`bookName`))"""
        )
    }
}
```

#### 4.2.3 表结构重构（复杂迁移）

**场景：** 需要修改主键、修改列类型、删除列（SQLite 不支持 ALTER TABLE DROP COLUMN）

**标准流程（4步）：**
```kotlin
// migration_13_14: 重构 books 表
private val migration_13_14 = object : Migration(13, 14) {
    override fun migrate(database: SupportSQLiteDatabase) {
        // 1. 创建新表
        database.execSQL(
            """CREATE TABLE IF NOT EXISTS `books_new` 
                (`bookUrl` TEXT NOT NULL, 
                 `name` TEXT NOT NULL,
                 ...
                 PRIMARY KEY(`bookUrl`))"""
        )
        
        // 2. 复制数据
        database.execSQL("INSERT INTO books_new SELECT * FROM books")
        
        // 3. 删除旧表
        database.execSQL("DROP TABLE books")
        
        // 4. 重命名新表
        database.execSQL("ALTER TABLE books_new RENAME TO books")
        
        // 5. 重建索引
        database.execSQL(
            "CREATE UNIQUE INDEX IF NOT EXISTS `index_books_name_author` ON `books` (`name`, `author`)"
        )
    }
}
```

#### 4.2.4 数据迁移与转换

```kotlin
// migration_18_19: 数据迁移 + 新增字段
private val migration_18_19 = object : Migration(18, 19) {
    override fun migrate(database: SupportSQLiteDatabase) {
        // 1. 创建新表（增加 androidId 字段）
        database.execSQL(
            """CREATE TABLE IF NOT EXISTS `readRecordNew` 
                (`androidId` TEXT NOT NULL, 
                 `bookName` TEXT NOT NULL, 
                 `readTime` INTEGER NOT NULL, 
                 PRIMARY KEY(`androidId`, `bookName`))"""
        )
        
        // 2. 迁移数据（插入新字段值）
        database.execSQL(
            """INSERT INTO readRecordNew(androidId, bookName, readTime) 
                SELECT '${AppConst.androidId}' as androidId, bookName, readTime 
                FROM readRecord"""
        )
        
        // 3. 删除旧表
        database.execSQL("DROP TABLE readRecord")
        
        // 4. 重命名
        database.execSQL("ALTER TABLE readRecordNew RENAME TO readRecord")
    }
}
```

**数据转换技巧：**
```kotlin
// 使用 ifNull 处理可能为空的字段
private val migration_32_33 = object : Migration(32, 33) {
    override fun migrate(database: SupportSQLiteDatabase) {
        // 从关联表获取数据填充
        database.execSQL(
            """INSERT INTO bookmarks (time, bookName, bookAuthor, ...)
                SELECT time, 
                       ifNull(b.name, bookName) bookName, 
                       ifNull(b.author, bookAuthor) bookAuthor,
                       ...
                FROM bookmarks_old o
                LEFT JOIN books b ON o.bookUrl = b.bookUrl"""
        )
    }
}
```

### 4.3 手动迁移集合管理

**DatabaseMigrations.kt 组织方式：**
```kotlin
object DatabaseMigrations {
    
    // 集中管理所有手动迁移
    val migrations: Array<Migration> by lazy {
        arrayOf(
            migration_10_11, migration_11_12, migration_12_13,
            migration_13_14, migration_14_15, migration_15_17,
            // ... 共 32 个迁移
            migration_42_43
        )
    }
    
    // 定义在 migrations 数组后
    private val migration_10_11 = object : Migration(10, 11) { ... }
    private val migration_11_12 = object : Migration(11, 12) { ... }
    // ...
}
```

### 4.4 版本跳跃处理

```kotlin
// 版本 15 直接跳到 17（跳过了 16）
private val migration_15_17 = object : Migration(15, 17) {
    override fun migrate(database: SupportSQLiteDatabase) {
        // 一次性完成版本 16 和 17 的变更
        // 如果用户从 15 升级，会执行这个迁移
        // 如果用户从 16 升级，也需要对应的 migration_16_17
    }
}
```

**⚠️ 警告：** 尽量避免版本跳跃，确保迁移路径连续。

## 五、自动迁移详解

### 5.1 自动迁移基础

Room 2.4.0+ 支持自动迁移，无需编写 Migration 类。

**支持的变更：**
- ✅ 添加新表
- ✅ 添加新列
- ✅ 删除列（需注解）
- ✅ 重命名列（需注解）

**不支持的变更：**
- ❌ 修改列类型
- ❌ 修改主键
- ❌ 需要数据转换

### 5.2 配置方式

```kotlin
@Database(
    version = 76,
    entities = [...],
    autoMigrations = [
        // 简单自动迁移（版本 43 → 44）
        AutoMigration(from = 43, to = 44),
        
        // 需要规范的自动迁移
        AutoMigration(
            from = 54, 
            to = 55, 
            spec = DatabaseMigrations.Migration_54_55::class
        ),
        
        // 删除列的自动迁移
        AutoMigration(
            from = 64, 
            to = 65, 
            spec = DatabaseMigrations.Migration_64_65::class
        )
    ]
)
abstract class AppDatabase : RoomDatabase() { ... }
```

### 5.3 自动迁移规范（AutoMigrationSpec）

#### 5.3.1 数据转换 - onPostMigrate

```kotlin
@Suppress("ClassName")
class Migration_54_55 : AutoMigrationSpec {
    
    override fun onPostMigrate(db: SupportSQLiteDatabase) {
        // 自动迁移完成后执行数据转换
        // 将旧的书源类型转换为新的书籍类型
        db.execSQL(
            """UPDATE books SET type = ${BookType.audio}
                WHERE type = ${BookSourceType.audio}"""
        )
        db.execSQL(
            """UPDATE books SET type = ${BookType.image}
                WHERE type = ${BookSourceType.image}"""
        )
        db.execSQL(
            """UPDATE books SET type = ${BookType.webFile}
                WHERE type = ${BookSourceType.file}"""
        )
        db.execSQL(
            """UPDATE books SET type = ${BookType.text}
                WHERE type = ${BookSourceType.default}"""
        )
        // 标记本地书籍
        db.execSQL(
            """UPDATE books SET type = type | ${BookType.local}
                WHERE origin LIKE '${BookType.localTag}%' 
                OR origin LIKE '${BookType.webDavTag}%'"""
        )
    }
}
```

**执行时机：**
```
用户升级：v54 → v55
    │
    ▼
Room 自动迁移表结构
    │
    ▼
执行 onPostMigrate（数据转换）
    │
    ▼
迁移完成
```

#### 5.3.2 删除列 - @DeleteColumn

```kotlin
@Suppress("ClassName")
@DeleteColumn(
    tableName = "book_sources",
    columnName = "enabledReview"
)
class Migration_64_65 : AutoMigrationSpec
```

**⚠️ 注意：** 删除列会丢失该列数据，谨慎使用。

#### 5.3.3 重命名列 - @RenameColumn

```kotlin
@RenameColumn(
    tableName = "books",
    fromColumnName = "old_name",
    toColumnName = "new_name"
)
class Migration_XX_YY : AutoMigrationSpec
```

### 5.4 自动迁移 vs 手动迁移

| 场景 | 推荐方式 | 示例 |
|------|---------|------|
| 添加列（可空） | 自动迁移 | `AutoMigration(from=44, to=45)` |
| 添加列（非空） | 自动迁移 | 设置 `@ColumnInfo(defaultValue)` |
| 删除列 | 自动迁移 + 注解 | `@DeleteColumn` |
| 重命名列 | 自动迁移 + 注解 | `@RenameColumn` |
| 数据转换 | 自动迁移 + Spec | `onPostMigrate` |
| 修改列类型 | 手动迁移 | 创建新表迁移 |
| 修改主键 | 手动迁移 | 创建新表迁移 |

## 六、迁移配置实战

### 6.1 完整配置示例

```kotlin
@Database(
    version = 76,
    exportSchema = true,
    entities = [Book::class, BookSource::class, ...],
    autoMigrations = [
        // 版本 43-76 的自动迁移
        AutoMigration(from = 43, to = 44),
        AutoMigration(from = 44, to = 45),
        // ... 更多自动迁移
        AutoMigration(from = 54, to = 55, spec = Migration_54_55::class),
        AutoMigration(from = 64, to = 65, spec = Migration_64_65::class),
        AutoMigration(from = 75, to = 76, spec = Migration_75_76::class),
    ]
)
abstract class AppDatabase : RoomDatabase() {
    
    companion object {
        val appDb by lazy {
            Room.databaseBuilder(appCtx, AppDatabase::class.java, "legado.db")
                // 1. 破坏性迁移（版本 1-9）
                .fallbackToDestructiveMigrationFrom(false, 1, 2, 3, 4, 5, 6, 7, 8, 9)
                // 2. 手动迁移（版本 10-43）
                .addMigrations(*DatabaseMigrations.migrations)
                // 3. 允许主线程查询（仅调试）
                .allowMainThreadQueries()
                // 4. 数据库回调
                .addCallback(dbCallback)
                .build()
        }
    }
}
```

### 6.2 迁移路径图

```
用户当前版本 → 目标版本 76

版本 1-9:    破坏性迁移 → 重建数据库（数据丢失）

版本 10-43:  手动迁移链
    v10 → v11 → v12 → ... → v43
    （依次执行每个 Migration）

版本 44-76:  自动迁移
    Room 自动处理结构变更
    + AutoMigrationSpec 数据转换
```

### 6.3 版本号管理

**递增规则：**
```
变更类型                    版本增量
─────────────────────────────────────
添加/删除表                  +1
添加/删除列                  +1
修改列类型                   +1
修改主键                     +1
数据转换                     +1
重构表结构                   +1
```

**Legado 版本历史：**
```
v1-9:   初始版本，破坏性迁移
v10:    开始使用手动迁移
v43:    最后一个手动迁移版本
v44:    开始使用自动迁移
v76:    当前版本
```

## 七、迁移测试与验证

### 7.1 测试迁移的重要性

**为什么必须测试？**
- 迁移失败会导致应用启动崩溃
- 数据丢失无法恢复
- 不同版本跳跃路径需要验证

### 7.2 手动测试步骤

```kotlin
// 1. 安装旧版本（v43）
// 2. 添加测试数据
// 3. 安装新版本（v44）
// 4. 验证数据完整性

// 测试要点：
// - 应用是否正常启动
// - 数据是否正确保留
// - 新功能是否正常
```

### 7.3 自动化测试

```kotlin
@RunWith(AndroidJUnit4::class)
class MigrationTest {
    @get:Rule
    val helper = MigrationTestHelper(
        InstrumentationRegistry.getInstrumentation(),
        AppDatabase::class.java,
        emptyList(),  // 自动迁移规范列表
        FrameworkSQLiteOpenHelperFactory()
    )

    @Test
    fun migrate43To44() {
        // 1. 创建版本 43 的数据库
        helper.createDatabase("test-db", 43).apply {
            // 插入测试数据
            execSQL("INSERT INTO books (bookUrl, name) VALUES ('test', 'Test Book')")
            close()
        }

        // 2. 运行迁移到版本 44
        val db = helper.runMigrationsAndValidate("test-db", 44, true)

        // 3. 验证数据
        val cursor = db.query("SELECT * FROM books")
        assertTrue(cursor.moveToFirst())
        assertEquals("Test Book", cursor.getString(cursor.getColumnIndex("name")))
        cursor.close()
    }
}
```

### 7.4 验证清单

| 检查项 | 说明 |
|--------|------|
| 应用启动 | 升级后是否正常启动 |
| 数据完整性 | 旧数据是否完整保留 |
| 默认值填充 | 新增字段是否正确填充 |
| 索引重建 | 索引是否正确创建 |
| 外键约束 | 外键关系是否正确 |
| 约束检查 | 唯一约束等是否生效 |

## 八、最佳实践与避坑指南

### 8.1 最佳实践

#### 1. 始终提供默认值

```kotlin
// ✅ 正确：非空列必须有默认值
@ColumnInfo(defaultValue = "0")
var order: Int = 0

// ❌ 错误：会导致迁移失败
var order: Int = 0  // 数据库层面没有默认值
```

#### 2. 版本号连续递增

```kotlin
// ✅ 推荐：版本连续
version = 43 → 44 → 45

// ❌ 避免：跳跃版本
version = 43 → 45（跳过 44）
```

#### 3. 先删除再插入（事务保证）

```kotlin
@Transaction
fun updateBookChapters(bookUrl: String, chapters: List<BookChapter>) {
    // 先删除
    deleteChaptersByBookUrl(bookUrl)
    // 再插入
    insertAll(chapters)
    // 原子性：要么都成功，要么都失败
}
```

#### 4. 保留迁移历史

```kotlin
// 不要删除旧迁移！
// 用户可能从任意旧版本升级
object DatabaseMigrations {
    val migrations = arrayOf(
        migration_10_11,  // 保留历史迁移
        migration_11_12,
        // ... 所有历史迁移
        migration_42_43
    )
}
```

### 8.2 常见错误与解决方案

#### 错误 1：缺少迁移

```
IllegalStateException: A migration from 43 to 44 was required but not found.
```

**解决：**
```kotlin
// 添加自动迁移配置
@Database(
    autoMigrations = [
        AutoMigration(from = 43, to = 44)  // ← 添加这行
    ]
)
```

#### 错误 2：默认值缺失

```
SQLiteException: Cannot add a NOT NULL column with default value NULL
```

**解决：**
```kotlin
// 添加 DEFAULT 值
database.execSQL(
    "ALTER TABLE table_name ADD column_name INTEGER NOT NULL DEFAULT 0"
)
```

#### 错误 3：数据类型不匹配

```
SQLiteException: table books has no column named price
```

**解决：**
- 检查实体类与迁移 SQL 是否一致
- 检查 schema 导出文件
- 清理重建项目

### 8.3 迁移调试技巧

```kotlin
// 1. 启用详细日志
Room.databaseBuilder(...)
```
